# GraD-Pert v2 来源门：最大可持续 batch 与 chunk 搭配

## 问题与约束

目标是在双 RTX 5090、完整预测＋SSL1＋SSL2、固定每卡累积 2 次、1000 表达查询基因和既定随机视图下，寻找**最大经过持续验证的物理微批**，并在可用容量内比较训练吞吐。全局 batch 为 `每卡微批 × 2 累积 × 2 卡`；单纯提高累积次数不计作 GPU 容量提高。所有候选启用图第 4 层来源逐维 key 门，保留单向 KDA 写入与最终状态读取、合法图邻域、λ₂=1、跨双卡 KoLeo 和原数据划分。不启动正式 B0。

先前旧图版本在每卡 66、全局 264 的 128 步容量测试通过；每卡 68、全局 272 在第 22 步 OOM。新来源门版本 `d2410efdc81a9690644ef2d165c2dea374ba0fbb` 的每卡 66 单步更新和 checkpoint 重载通过，峰值预留约 31.43 GB/卡。旧版本的容量边界不能直接转移到新版本。

## 候选和验收顺序

以新来源门的默认 `scan32 / sequence32 / graph_rows64` 为锚。自包含配置在 `configs/v2/source_key_gate_capacity_jurkat/`，仅改变微批、图目标行块或序列扫描块：

| 每卡微批 | 全局 batch | 图扫描 | 序列扫描 | 图目标行块 | 用途 |
| ---: | ---: | ---: | ---: | ---: | --- |
| 66 | 264 | 32 | 32 | 64 | 当前单步通过的锚点 |
| 67/68/70 | 268/272/280 | 32 | 32 | 64 | 查容量边界 |
| 68/70 | 272/280 | 32 | 32 | 32 | 减小并行图目标块的显存压力 |
| 68/70 | 272/280 | 32 | 16 | 64 | 减小长序列分块临时量 |
| 66 | 264 | 32 | 32 | 96/128 | 查已观察到的图目标并行提速能否在大 batch 成立 |

单步筛选开始后观察到：微批70时序列块由32改16，使峰值预留从约32.35 GB/卡降至28.90 GB/卡；图行64改32的峰值不变。因此追加序列16的微批72/74/76/77/78/80，以及序列32的微批72作为边界对照。追加不是宣称这些配置稳定或更快；只在新发布提交上用独立ID筛选。

按资源和收据逐级运行：先做双卡单步完整更新排除明显 OOM；对有竞争力的最大微批做至少 128 次连续更新、checkpoint 续跑和 300-control 推理；对能持续的组合在**相同全局 batch**下做多步端到端吞吐比较。每次使用干净已发布 Git SHA、独立 run ID 和配置 SHA，保留失败收据。只因短测通过不得称为最大可持续 batch。比较输出/梯度时区分浮点求和顺序、目标行块重排随机数与数学模型改变；行块 96/128 在旧严格语义审计中未过逐目标随机分配，因此其速度数据只能作为调度候选，不能直接纳入正式等价默认。

最终选择须同时报告：通过的最高持续微批、失败上界、双卡含数据等待 cells/s、峰值已分配/预留显存、启动和稳态时间、来源/配置哈希，以及是否保留原 chunk 默认。如果更大物理 batch 降低总吞吐或显存余量不足，会把“容量最大”和“实用训练配置”分开报告。

追加候选使用已发布且服务器干净的 `8dfb267adb25591393602066ef1226e7cbb76174`，publication 收据 SHA256 为 `37024a734ded09bd76b1e4060aaa2b4b1fe1eac6c005f2844664d9bb1ea2ff57`。双卡单步完整更新中，图目标行块 64、序列块 16 的每卡微批 72/74/76/77/78/80 均通过；序列块 32 的微批 72 也通过。微批 77 的单步日志曾出现 expandable-segments 映射 OOM 警告，虽最终状态为 passed，不视为安全容量证据。各候选使用独立 `v2-gate-capacity-8dfb267-{variant}-integration-r1` 收据。

## 相同完整更新路径的吞吐排序与 B0 选型

在同一发布源码上，双卡 `benchmark-only` 每项做 12 次完整预测＋SSL1＋SSL2 更新，前 2 次热身，之后 10 次测含数据等待的 cells/s。独立运行 ID 为 `v2-gate-capacity-8dfb267-{variant}-bench12-r1`；队列日志 `v2-gate-capacity-8dfb267-throughput-bench12-r1.log`，队列退出 0，各项另存 `.exit` 与 receipt。最后复测第一个配置以检查运行顺序漂移。

| 每卡微批 | 图目标行块 | 序列块 | 完成步数 | 含数据等待 cells/s | 峰值预留 GB/卡 | 结果 |
| ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 74 | 64 | 16 | 12/12 | 13.794 | 31.048 | 通过 |
| 72 | 64 | 16 | 12/12 | 13.287 | 31.040 | 通过 |
| 70 | 64 | 16 | 12/12 | 12.623 | 30.484 | 通过 |
| 70 | 64 | 32 | 1/12 | — | — | CUDA OOM；需 118 MiB 时仅余约 14 MiB |
| 66 | 64 | 32 | 12/12 | 12.687 | 31.482 | 通过 |
| 74（复测） | 64 | 16 | 12/12 | 13.791 | 31.048 | 通过 |

因此，在**本次所测候选**里选择 `m74 × accumulation2 × 2 GPUs = global batch296`、图 KDA 扫描块32、图目标行块64、序列 KDA 扫描块16。m74 两次短测均值13.792 cells/s，相比旧默认 m66/seq32 的12.687高约8.7%；m74另已通过128步持续测试，较大的m76首先在第14次更新OOM。短测吞吐提升不证明三轮模型效果；m74在持续测试的峰值预留32.621GB/卡，余量有限，需要正式训练继续监测。rows96/128虽然先前有提速迹象，但逐目标随机数语义尚未过审计，不纳入本次等价选型。用户随后授权独立的三轮完整B0；其配置基于上述m74，只调整固定训练预算为3 epoch，保持预测＋SSL1＋SSL2与损失权重不变。
